Actividades ↔ Insumos: opciones de diseño

Cuatro formas de modelar la relación entre las actividades a campo y los insumos que consumen, con sus trade-offs y lo que necesitamos preguntar antes de elegir una.

El problema

En el enunciado hay dos relaciones, no una

Hoy cada actividad y cada uso de insumo es una entry suelta de structured data con su propio UUID. Los items de la actividad nombran al insumo como texto libre. Leyendo el enunciado completo aparecen dos vínculos distintos, y el diseño tiene que cubrir los dos.

R1 · item → insumo de inventario

El item fertilizers[0].source = "Urea" se vincula con el insumo Urea del inventario solo si el nombre coincide. De acá salen la unidad, la cantidad aplicada y el costo.

R2 · actividad → SUPPLYOUTPUT

Al marcar «Descontar del inventario» se genera un uso de insumo. El tab Datos necesita saber que sd-supply-777 es hijo de sd-fert-002. Hoy ese vínculo no existe.

Lo que condiciona cualquier opción

  • Los items no tienen idfertilizers[], treatments[] y products[] son listas sin identificador. En un update hay que decidir cómo reconocer cada item: por posición, por nombre o con un item_id nuevo.
  • La genética no es una listadetails.genetic_variety es un campo suelto. El modelo tiene que aceptar items que no vienen de un array.
  • Las unidades no se parecenAgro usa dosis por hectárea (2 L/ha × 25 ha = 50 L). Hacienda usa dosis absolutas (ml, cc, g) y lotes sin hectáreas. El inventario tiene su propia unidad (Litros, Kilos, Rollos).
  • SUPPLYOUTPUT ya apunta por idSus records[] tienen supply_id pero no nombre. Para ese tipo el vínculo con el insumo es directo.

A

Tabla de link a nivel item

Recomendada

Una tabla relacional activity_supply_link con una fila por item linkeado. La escribe la capa de servicio en la misma transacción que la structured data. La relación con el SUPPLYOUTPUT (R2) va en la misma fila, en supply_output_id.

erDiagram
    STRUCTURED_DATA ||--o{ ACTIVITY_SUPPLY_LINK : "activity_id"
    SUPPLY ||--o{ ACTIVITY_SUPPLY_LINK : "supply_id"
    STRUCTURED_DATA ||--o| ACTIVITY_SUPPLY_LINK : "supply_output_id"
    STRUCTURED_DATA {
        uuid id PK
        string structure_type
        uuid field_id
        date record_date
        jsonb data
    }
    SUPPLY {
        string id PK
        uuid field_id
        string name
        int unit
    }
    ACTIVITY_SUPPLY_LINK {
        uuid id PK
        uuid activity_id FK
        string item_path
        int item_index
        string item_name
        string supply_id FK
        decimal dosage
        string dosage_units
        decimal quantity
        int unit
        uuid supply_output_id FK
        uuid field_id
        date record_date
    }
  
# Índices
UNIQUE (activity_id, item_path, item_index)
INDEX  (supply_id, record_date)      # ¿dónde se usó este insumo?
INDEX  (field_id, record_date)       # reportes por campo / lote
INDEX  (supply_output_id)            # armar padre-hijo en el BFF

def update_activity(sd_id, new_structure):
    with tx():
        sd = repo.update(sd_id, new_structure)              # la actividad manda
        desired = build_links(sd, supplies_by_name(sd.field_id))
        current = link_repo.by_activity(sd_id)
        reconcile(current, desired)                          # diff: insert / update / delete

A favor

  • Relación explícita, con FK e índices. Sumar cantidades o costos es SQL simple.
  • Una sola fila cubre R1 y R2.
  • Copiar field_id y record_date en la tabla permite hacer reportes sin tocar el JSON.
  • Es fácil de explicar y de defender en la entrevista.

En contra

  • Se escribe en dos lugares (JSON y tabla). Hay que hacerlo en la misma transacción para que no se desincronicen.
  • Si el item se identifica por posición, reordenar la lista rompe la reconciliación.
  • item_path como string es algo genérico.

Preguntas para poder hacer esta opción

  1. ¿Structured data y el inventario están en la misma base relacional? Define si podemos tener FK reales y escribir todo en una transacción.
  2. ¿Podemos agregar un item_id estable a cada item de la lista? Si no, reconciliamos por posición + nombre y lo documentamos como limitación.
  3. ¿Puede una actividad tener dos items con el mismo insumo (Urea dos veces con dosis distintas)? Define la clave única de la tabla.
  4. ¿Una actividad en varios lotes genera un SUPPLYOUTPUT o uno por lote? SUPPLYOUTPUT.basic_info.lote es un único string; puede que R2 sea 1 a N.
  5. Si se renombra el insumo, ¿el link se mantiene (ya tenemos el supply_id) o se rompe porque la regla es por nombre?
B

Referencia embebida en el JSON

Más simple

Cada item del schema suma un supply_id resuelto al momento de escribir, como ya tiene Record. El SUPPLYOUTPUT suma un origin_activity_id. Para consultar se usan índices sobre el JSON (GIN o columnas generadas).

class Fertilizer(BaseModel):
    source: str
    supply_id: Optional[str] = None        # NUEVO · se resuelve al escribir por nombre
    dosage: Optional[float] = None
    dosage_units: Optional[Literal["L/ha", "kg/ha"]] = None

class SUPPLYOUTPUT(BaseStructure):
    basic_info: BasicInfo
    origin_activity_id: Optional[UUID] = None   # NUEVO · R2
    records: list[Record] = []

-- consulta: ¿qué actividades usaron el insumo X?
CREATE INDEX ON structured_data USING gin ((data -> 'fertilizers') jsonb_path_ops);

A favor

  • Hay una sola fuente de verdad, así que no puede haber diferencias entre dos copias.
  • El item y su link viajan juntos, así que desaparece el problema de identificar el item en un update.
  • El front recibe el item con su insumo ya resuelto.

En contra

  • Queda cerca de lo que el enunciado pide evitar: la relación vive dentro del JSON.
  • No hay FK. Si se borra un insumo, el id queda colgado.
  • Hace falta un índice por cada path de cada tipo, y las agregaciones son caras.
  • Obliga a migrar y versionar los cinco schemas.

Preguntas para poder hacer esta opción

  1. ¿Qué motor guarda structured data: Postgres JSONB, Mongo u otro? Sin índices sobre JSON esta opción no es consultable.
  2. ¿Podemos cambiar los schemas? ¿Hay versionado, apps mobile offline o clientes viejos que los consuman?
  3. ¿Qué volumen de datos y qué consultas se esperan (reportes de costo por campaña, stock)? Si hay muchas agregaciones, B se queda corta.
  4. Si se borra un insumo del inventario, ¿qué pasa con las actividades que lo referencian?

Conviene si el motor es documental y el uso principal es mostrar la actividad, no hacer reportes. También sirve como complemento de A: guardar el supply_id en el item como snapshot para el front.

C

Proyección por eventos

Evolución

La structured data no cambia. Cada alta, edición o baja publica un evento mediante un outbox. Un proceso de linkeo aplica la regla de matching y mantiene la tabla de links (la misma de A) o directamente un read model listo para el tab Datos.

sequenceDiagram
    participant API
    participant SD as structured_data
    participant OB as outbox
    participant W as Linker
    participant L as tabla de links
    API->>SD: alta / edición / baja de actividad
    API->>OB: evento StructuredDataChanged (misma tx)
    W->>OB: consume el evento
    W->>W: extrae items y matchea por nombre
    W->>L: upsert / reconcilia links
    Note over W,L: también escucha SupplyCreated y SupplyRenamed para re-matchear

A favor

  • El linkeo queda fuera del camino de escritura.
  • Si un insumo se crea o se renombra después, el re-match sale solo.
  • Para procesar el histórico alcanza con re-procesar los eventos.

En contra

  • La consistencia es eventual: el usuario guarda y el link aparece un rato después.
  • Necesita más infraestructura: outbox, worker, reintentos e idempotencia.
  • Es más difícil de seguir y de debuggear. Para el alcance del challenge es demasiado.

Preguntas para poder hacer esta opción

  1. ¿Ya existe infraestructura de eventos u outbox (colas, workers)? Si no existe, el costo de C se multiplica.
  2. ¿Es aceptable que el tab Datos muestre la actividad sin sus insumos durante unos segundos?
  3. ¿Producto quiere linkeo retroactivo? Por ejemplo, cargo «Urea» como texto libre y después creo «Urea» en el inventario.
  4. ¿Hay que linkear el histórico ya cargado (backfill)? ¿Cuántos registros son?

Encaja como segunda etapa de A: el linkeo sincrónico se queda y se suma un job o worker para re-matcheo y backfill.

D

Tabla genérica de relaciones

Descartable

Una sola tabla de aristas structured_data_relation que vincula cualquier par de entries con un tipo de relación: CONSUMES_SUPPLY, GENERATED_OUTPUT y, más adelante, otras como cosecha → siembra.

erDiagram
    STRUCTURED_DATA ||--o{ SD_RELATION : "source_id"
    STRUCTURED_DATA ||--o{ SD_RELATION : "target_id"
    SD_RELATION {
        uuid id PK
        uuid source_id
        string target_id
        string relation_type
        string source_item_ref
        jsonb metadata
    }

A favor

  • Se pueden sumar relaciones nuevas sin crear tablas.
  • Hay una sola forma de preguntar qué está relacionado con X.

En contra

  • Es polimórfica: no hay FK reales y target_id apunta a veces a SD y a veces a inventario.
  • Cantidad, unidad y costo terminan en metadata, otra vez como JSON sin tipar. Eso es justo lo que queremos consultar.
  • Es una abstracción antes de tiempo.

Preguntas para poder hacer esta opción

  1. ¿Hay otras relaciones entre entries en el roadmap, como cosecha con siembra o labor con contratista? Si no hay, la generalidad no paga.
  2. ¿Las consultas de cantidad y costo son prioritarias? Si lo son, D obliga a abrir metadata, igual que hoy con el JSON.
Aplican a cualquier opción

Preguntas comunes

Estas definen el comportamiento del modelo sin importar qué opción elijamos. Las marcadas como clave cambian el diseño. Si no nos responden, las fijamos como supuestos en el README.

Regla de matching

  1. ¿«Mismo nombre» es igualdad exacta o normalizada (mayúsculas, espacios, acentos)? clave
  2. ¿Contra qué inventario se busca: el del campo, el del establecimiento o el de la cuenta? clave
  3. ¿Los nombres de insumo son únicos en ese alcance? Si hay dos «Urea», ¿cuál se usa?
  4. Si el usuario eligió el insumo con «Seleccionar de inventario», ¿manda el id elegido o igual se aplica el match por nombre?

Alta, edición y baja

  1. ¿La actividad es la fuente de verdad sobre sus insumos? Si cambio la dosis, ¿se recalcula el SUPPLYOUTPUT y el stock? clave
  2. Si saco un item de la actividad, ¿se borra su SUPPLYOUTPUT y se repone el stock?
  3. ¿El borrado es físico o lógico? Al borrar la actividad, ¿el SUPPLYOUTPUT se borra, se repone o queda como fila suelta? clave
  4. ¿Se puede editar el SUPPLYOUTPUT hijo por separado? ¿Qué pasa si queda distinto de la actividad?

Unidades, cantidad y costo

  1. ¿Cómo se convierte la dosis a la unidad del insumo (L/ha × ha → Litros; cc/ha → Litros; g/ha → Kilos)?
  2. En hacienda, ¿la dosis es por cabeza o total?
  3. Para la genética: ¿cómo se pasa de semillas/ha a la unidad del insumo semilla (bolsas, kg)?
  4. ¿El costo sale de un precio del insumo (último o promedio ponderado)? ¿Se congela a la fecha de la actividad?
  5. ¿Qué valores tiene el enum de Record.unit?

Tab «Datos»

  1. ¿El front prefiere un bloque children genérico o un supplies tipado?
  2. ¿total y la paginación cuentan solo filas padre? ¿Y new_records?
  3. Si el SUPPLYOUTPUT tiene otra fecha que su actividad, ¿se muestra igual anidado?
  4. ¿Mostramos los items sin match (texto libre) como «insumo no inventariado»?

Dirección propuesta

A como base: tabla de link por item, escrita en la misma transacción y con la actividad como fuente de verdad. De B tomamos el supply_id como snapshot dentro del item si al front le sirve. C queda en el README como evolución para re-matcheo y backfill. D se menciona como alternativa descartada y se explica por qué.

Mientras no haya respuestas, el supuesto es: match exacto después de normalizar (trim y minúsculas), inventario del campo, un SUPPLYOUTPUT por actividad, y la baja de la actividad hace baja lógica de sus links y de su SUPPLYOUTPUT.
